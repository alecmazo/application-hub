# MarinFC-reports

Static reports for Marin FC B2013-14 Blue, served at `/MarinFC-reports/` (live: `https://alecmazo.github.io/application-hub/MarinFC-reports/`).

`index.html` is the hub: Game Reports on one side, Trends on the other (tabs on a narrow screen). Game reports are listed newest first with opponent, date, and score. Do not add a link to this section from the public application-hub home page.

Each report page is standalone HTML. It links back only to this hub (`../`) and has a Print / Save PDF button that calls `window.print()`. A low-emphasis Request delete control on the hub cards and on each report bar asks for confirmation, then opens a prefilled GitHub issue; the report is removed after review, not immediately. Those issue URLs include `assignees=alecmazo` so an `assigned` event can wake automation. The hub also has a prominent New game report from Veo button (above the Game Reports and Trends columns, hidden in print). It prompts for an optional opponent, date, or Veo match link, asks for confirmation, then opens a prefilled issue with label `generate-report` and assignee `alecmazo`. That request means: pull the Veo match report, build the game report, update Season Trend, Player Cards and Pro-Style Analytics, and open a PR. Nothing is published until the PR is approved. Print CSS hides that chrome and the in-page contents nav, keeps chart and row breaks from splitting awkwardly, uses Letter paper, and sets `print-color-adjust: exact`. Every report and the hub include:

```html
<meta name="robots" content="noindex,nofollow">
```

Do not add this path to a sitemap.

Files live in `public/MarinFC-reports/` so the GitHub Pages build copies them as-is. Do not add this path to the SPA deep-route copy in `vite.config.spa.ts` — that would replace the hub with the app.

## Add a report

1. Pick a folder name: a readable slug, a hyphen, then a random suffix of at least 8 characters.

   ```bash
   openssl rand -hex 6
   ```

   Example: `passing-and-control-91f2292b8b5f`.

2. Create `public/MarinFC-reports/<folder>/index.html`. Keep the page self-contained. It must include the robots meta, a Print / Save PDF button, and a relative "All reports" link to this hub (`../`). In-page anchors (`#section`) are fine. Do not link to the public application-hub home page.

3. Append one object to the `reports` array in `reports.json`:

   ```json
   {
     "slug": "readable-name-0123456789ab",
     "title": "Report title",
     "date": "2026-11-10",
     "description": "One or two sentences shown on the card."
   }
   ```

   `slug` must match the folder name. `date` is `YYYY-MM-DD`.

4. If it is a per-game report, also add the game id and live slug to `GAME_SLUGS` in the local generator (`/workspace/veo/share/season_reports.py`) so the hub lists opponent, date, and score. If it is a trend/analysis page, add it to `TREND_REPORTS`. Then regenerate the hub.

5. Do not add the report, or this section, to a sitemap.

Push to `main`. The Pages workflow publishes `public/` with the rest of the site.

## Season trend report (stable slug)

`season-trend-ab0e5977a9e9` is the year-to-date season trend report. Keep that folder name. After every future game, overwrite `public/MarinFC-reports/season-trend-ab0e5977a9e9/index.html` in place (keep the Print / Save PDF chrome) and update that entry's `date` in `reports.json` (and the description if the summary changes). The live URL stays `https://alecmazo.github.io/application-hub/MarinFC-reports/season-trend-ab0e5977a9e9/`. Per-game reports still get a new folder each time.

## Player cards and pro-style analytics (stable slugs)

- `player-cards-4333cd65c796`: Player Cards (YTD). Every rostered player gets an FC-style card with an overall and six face stats (PAC, SHO, PAS, DRI, DEF, PHY). Each stat is `40 + 50 × squad percentile` of per-70 Veo inputs, and the pool is outfield players with at least 60 capped minutes. The overall is a role-weighted average of the face stats. The full formula is printed on the page. Goalkeepers have no overall because Veo has no save data.
- `pro-analytics-6feface8946d`: Pro-Style Analytics (YTD). Team metrics, opponent profiles, rule-based shape options, a per-70 player table with weighted turnovers v1 and v2, role fit, and a Methodology section. The Methodology section lists which pro metrics (xT, PPDA, field tilt, progressive passes, line breaks and so on) are implemented, approximated or out of reach with Veo data, and it carries the passing weights and their sources.

Both pages are generated by `/workspace/veo/share/pro_metrics.py`. `season_reports.py` always calls `build_ytd_pages()`, so adding a new game and running the generator rebuilds Season Trend, Player Cards and Pro-Style Analytics together from the full season file. Each statistic uses every game that has that field; there is no last-N cutoff. Overwrite the live folders in place and keep the slugs.
